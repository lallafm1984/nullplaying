# FrameSmith 16프레임 Detailed 스프라이트 재사용 런북

이 문서는 NULL PLAYING의 다른 스킬도 현재 전사 돌진 계열과 같은 규격으로 바로 생성·동기화·웹 검증하기 위한 작업 계약이다. 새 세션에서는 이 문서를 먼저 읽고, Android 리소스가 아니라 `tools/vfx-lab`의 웹 스킬 테스트 페이지에 먼저 적용한다.

호출 별칭: 사용자가 `스프라이트 생성기`라고 말하면 전역 개인 스킬 `$sprite-generator`가 이 문서와 현재 작업 상태를 불러와 같은 흐름을 실행한다.

원 작업 컨텍스트: `019ffe3d-f472-7973-8eff-c61422f384df`

## 1. 고정 제작 규격

| 항목 | 고정값 |
|---|---|
| 렌더링 모드 | `Detailed` (`mode: "detailed"`) |
| 픽셀 아트 | 금지 |
| 프레임 | 정확히 16장 |
| 배열 | 4열 × 4행, row-major |
| 프레임 크기 | 361 × 160 px |
| 시트 크기 | 1444 × 640 px |
| 배경 | 투명 RGBA |
| 재생 속도 | 16 fps, 프레임당 62.5 ms |
| 전체 길이 | 1,000 ms |
| 반복 | `false` |
| 카메라 | 모든 프레임에서 고정 |
| 웹 보간 | `image-rendering: auto` |

시트에는 격자선, 프레임 번호, 테두리, 여백, 검정/흰 배경을 넣지 않는다. F01과 F16은 대부분 투명해야 하며, F08은 주 타격, F09는 최대 타격으로 설계한다.

## 2. 프롬프트 3단 구조

FrameSmith의 세 필드는 역할을 섞지 않는다.

1. `commonPrompt`: 화면 규격, 16프레임 시간축, 카메라, 공통 동작 문법, 투명도, UI 가독성 등 배치 전체 계약.
2. `generationPrompt`: 한 스킬만의 실루엣, 깊이, 충돌 방식, 색상, 위력 단계, 금지 오브젝트.
3. `negativePrompt`: 픽셀 아트, 캐릭터/배경/UI/글자, 잘못된 프레임 수·순서, 격자·테두리·불투명 배경 등 공통 실패 조건.

전사 계열의 신규 공통 동작 문법은 아래 다섯 가지다. 모두 좌→우로 자산을 이동시키는 방식이 아니라 고정된 화면 중심 `x=50%, y=55%`에서 깊이·충돌·파열을 구성한다.

| 후보 | 계열 문법 | 새 연출 원칙 |
|---|---|---|
| `c01` | `SOVEREIGN_RIFT_CLEAVE` | 서로 다른 깊이의 곡면 강철 압력날이 중심에서 맞물려 화면을 큰 절단면으로 분리한다. |
| `c02` | `TITAN_SKYFALL_CRUSH` | 상부의 압축 질량과 수직 충돌 기둥이 중심을 짓누르고 다층 충격파로 해방된다. |
| `c03` | `CENTER_BREAKTHROUGH` | 중심 소실점에 힘이 수렴한 뒤 관객 방향으로 돌파하고 잔해·속도선이 외곽으로 커진다. |
| `c04` | `TECTONIC_REBIRTH` | 지면 압력이 중심으로 모인 뒤 서로 다른 지형판·암반 리브·지진 테두리로 재구성되어 솟는다. |
| `c05` | `CENTERED_BATTLE_TEMPEST` | 좌→우 반복 참격 대신 서로 다른 깊이의 곡선·사선 압력날이 중심을 둘러싸며 실제 타격 수 리듬으로 충돌한다. |

`c01`, `c02`, `c04`, `c05`를 새로 만들 때는 기존 NULL PLAYING 스킬 이미지·액션 태그·방향 태그·색상·실루엣·타이밍을 입력 근거로 쓰지 않는다. `catalogId`, 한국어 스킬명, 레벨, 위력 단계와 `c05`의 실제 타격 수만 정체성 입력으로 사용한다.

전사 돌진 기본 배치는 `charge-sprite-prompts.json` / `charge-sprite-jobs.json`, 화면 점유·가로 늘어짐·최종기 개선을 반영한 최신 배치는 `charge-sprite-revision-prompts.json` / `charge-sprite-revision-jobs.json`이 기준이다.

## 3. 새 스킬 배치 만들기

1. `sprite-prompts.template.json`을 `<배치명>-sprite-prompts.json`으로 복사한다.
2. `templateOnly`를 `false`로 바꾼다.
3. 모든 `{{PLACEHOLDER}}`를 실제 값으로 교체한다.
4. `catalogId`는 Android/Web에서 함께 쓰는 안정 ID를 그대로 사용한다. 화면에 표시되는 스킬명만으로 파일을 식별하지 않는다.
5. 같은 동작 문법을 쓰는 스킬은 `commonPrompt`를 공유하고, 차이는 각 `generationPrompt`에만 작성한다.

큐에 넣기 전에는 반드시 드라이런으로 규격과 플레이스홀더를 검증한다.

```bash
SPRITE_PROMPT_MANIFEST=tools/vfx-lab/<배치명>-sprite-prompts.json \
SPRITE_JOBS_OUT=tools/vfx-lab/<배치명>-sprite-jobs.json \
SPRITE_OUTPUT_DIR=tools/vfx-lab/custom-assets/<배치명> \
SPRITE_DRY_RUN=1 \
node tools/vfx-lab/queue_sprite_sheets.mjs
```

## 4. FrameSmith 안전 규칙과 생성

FrameSmith 주소는 `http://127.0.0.1:4317`이다. 생성 전 `/api/health`를 확인한다.

```bash
curl http://127.0.0.1:4317/api/health
```

`activeJobId`가 `null`이 아니면 기존 작업을 중지·재시작·교체하지 않는다. 새 작업은 대기열에 추가할 수 있으며, 게이트웨이가 한 건씩 순차 실행한다.

실제 생성 명령:

```bash
SPRITE_PROMPT_MANIFEST=tools/vfx-lab/<배치명>-sprite-prompts.json \
SPRITE_JOBS_OUT=tools/vfx-lab/<배치명>-sprite-jobs.json \
SPRITE_OUTPUT_DIR=tools/vfx-lab/custom-assets/<배치명> \
node tools/vfx-lab/queue_sprite_sheets.mjs
```

일부만 큐에 넣을 때는 `SPRITE_FROM_INDEX`와 `SPRITE_JOB_LIMIT`을 함께 쓴다. 이미 작업 JSON에 있는 `catalogId`는 중복 생성하지 않는다.

```bash
SPRITE_FROM_INDEX=5 SPRITE_JOB_LIMIT=3 ... node tools/vfx-lab/queue_sprite_sheets.mjs
```

## 5. 결과 자동 동기화

생성이 끝난 PNG만 내려받고, Detailed·16프레임·4×4·1444×640 계약을 자동 검증한다.

```bash
SPRITE_JOBS_MANIFEST=tools/vfx-lab/<배치명>-sprite-jobs.json \
SPRITE_WATCH=1 \
node tools/vfx-lab/sync_sprite_sheets.mjs
```

출력 위치는 작업 JSON의 `outputDir`에 기록된다. 이미 내려받은 정상 PNG는 다시 다운로드하지 않는다. 실패 또는 취소 작업이 있으면 동기화 프로세스는 오류 코드로 종료한다.

현재 전사 돌진 배치는 기존 전용 도구도 그대로 유지한다.

- 기본 프롬프트 / 작업 ID: `charge-sprite-prompts.json` / `charge-sprite-jobs.json`
- 최신 개선 프롬프트 / 작업 ID: `charge-sprite-revision-prompts.json` / `charge-sprite-revision-jobs.json`
- 큐: `queue_charge_sprites.mjs`
- 동기화: `sync_charge_sprites.mjs`
- 기본 출력: `custom-assets/warrior-charge/<catalogId>.png`
- 최신 개선 출력: `custom-assets/warrior-charge-revision/<catalogId>.png`

전사 비돌진 80종 신규 배치는 `build_warrior_reinvention_manifests.mjs`로 카탈로그에서 결정적으로 재생성한다.

- 베기: `warrior-cleave-sprite-prompts.json` / `warrior-cleave-sprite-jobs.json` / `custom-assets/warrior-cleave/`
- 내려찍기: `warrior-crush-sprite-prompts.json` / `warrior-crush-sprite-jobs.json` / `custom-assets/warrior-crush/`
- 지진: `warrior-earth-sprite-prompts.json` / `warrior-earth-sprite-jobs.json` / `custom-assets/warrior-earth/`
- 난격: `warrior-flurry-sprite-prompts.json` / `warrior-flurry-sprite-jobs.json` / `custom-assets/warrior-flurry/`

## 6. 웹 스킬 테스트 페이지 적용

1. 생성 PNG를 `tools/vfx-lab/custom-assets/<배치명>/<catalogId>.png`에 둔다.
2. `app.js`의 해당 자산 Map에 `catalogId → URL`을 등록한다.
3. 파일이 실제로 존재하고 시트 검증이 끝난 ID만 ready Set에 넣는다. 아직 없는 ID를 먼저 활성화하면 기존 VFX까지 숨겨져 빈 화면이 된다.
4. 4×4 시트는 `361 × 160` 캔버스에 프레임당 `62.5 ms`로 잘라 그린다.
5. `styles.css`는 `image-rendering: auto`를 유지한다. `pixelated` 또는 nearest-neighbor 설정을 사용하지 않는다.
6. 코드 변경 뒤 스크립트 쿼리의 캐시 버전을 올리고 브라우저를 새로고침한다.

로컬 테스트 주소: `http://127.0.0.1:4173/`

현재 전사 공용 스프라이트 구현 위치:

- 캔버스: `index.html`의 `#chargeSprite`
- 16프레임 재생기와 자산 등록: `app.js`의 `WARRIOR_SPRITES`, `WARRIOR_READY_SPRITES`, `renderWarriorSprite`
- 표시 규칙: `styles.css`의 `.charge-sprite`

## 7. 검증 체크리스트

- [ ] FrameSmith 작업 모드가 `Detailed`인가?
- [ ] PNG가 1444×640, RGBA, 4×4, 16프레임인가?
- [ ] 픽셀 아트·nearest-neighbor 계단 현상이 없는가?
- [ ] F01→F16이 시간 순서대로 이어지고 중복·누락이 없는가?
- [ ] F08/F09 주 타격의 방향과 중심축이 스킬 문법에 맞는가?
- [ ] 중심부를 포함한 화면 점유율과 충격 밀도가 충분한가? (스킬명·피해 숫자 가림은 검수 기준에서 제외)

- [ ] 웹 검증이 끝나기 전 Android 리소스를 수정하지 않았는가?

## 9. 현재 작업 경계

전사 돌진 계열은 `전열 돌진`부터 `불퇴 대돌파`까지 19개가 `CENTER_BREAKTHROUGH` 문법으로 생성·동기화·ready 활성화까지 완료됐다.

2026-08-16 화면 점유·늘어짐 개선 배치에서 `맹진 찌르기`, `전차 충돌`, `선봉 쇄도`, `철혈 관통`, `군단 대돌파`, `군왕 돌진`, `성채 대돌파`, `용살 쇄도`, `패왕 대진군`, `천하무패 돌격` 10개를 재생성·생성했다. 모두 Detailed·16프레임·4×4·1444×640 RGBA이고 FrameSmith 결과는 완료 10, 실패 0, 취소 0이다. 웹 테스트 페이지에 우선 적용했으며 10개 모두 490ms `CHARGE · CENTER_BREAKTHROUGH` 상태를 확인했고, `천하무패 돌격`은 420/490/720ms를 별도 검증했다.

이후 재사용 규칙:

- 화면을 채울 때 한 개체를 확대하지 말고, 전경·중경·후경 레이어를 자연 비율로 배치해 시트 가장자리에서 잘리게 한다.
- 가로 늘어짐은 분리된 곡면 충격파와 자연 두께의 원근 조각으로 해결하고, 한 줄의 파노라마 흐림을 피한다.
- 스킬명·피해 숫자 가림은 검수 기준에서 제외하고, 중심부까지 충격 밀도를 우선한다.
- Android 전투 화면 적용은 아직 하지 않았다. 이 웹 1차 검증 이후 별도 단계다.

## 10. 프레임 경계·중심축 QA와 수정 배치

웹 재생 중 하단에 다른 프레임처럼 보이는 띠가 나타나면 먼저 렌더러 자르기 좌표와 원본 시트를 분리해 진단한다. 공용 렌더러는 1444×640 시트를 정확히 4열×4행으로 나눠 `sourceX = column × 361`, `sourceY = row × 160`을 사용한다. 원본 PNG가 정확한 크기인데 개별 361×160 프레임 안에도 하단 띠가 남아 있으면 자르기 오류가 아니라 생성된 셀 자체의 경계 오염이다.

진단 명령:

```bash
python3 tools/vfx-lab/audit_sprite_frames.py \
  --output-dir tools/vfx-lab/evidence/frame-audit \
  tools/vfx-lab/custom-assets/<배치명>/<catalogId>.png
```

이 도구는 원본을 수정하지 않고 16개 프레임 몽타주와 다음 수치를 만든다.

- 상·하단 4px의 알파 점유율
- 프레임 전체 알파 점유율과 평균 알파
- 알파 영역의 점유 폭·높이
- 좌우 알파 대칭률
- 전체 알파 중심점
- 가장 밝은 15% 픽셀의 중심점과 프레임 간 X 이동량
- 고정 중심선 `x=50%`가 표시된 개별 프레임

보고서의 `qaSignals`는 F01/F16 잔존, F08/F09 화면 미점유, 피크 한쪽이라도 좌우 알파 대칭률 90%를 넘는 거울대칭, 피크 발광핵 이탈, F08이 F09보다 강한 최대 타격 순서 위반, F10~F12가 F09 최대 타격을 추월하는 지연 피크, F12 이후 에너지·점유·대칭 구조 재증가를 ‘우선 시각검수’ 대상으로 표시한다. 이 신호는 자동 합격/불합격 판정이 아니며 최종 판단은 몽타주와 웹 재생을 기준으로 한다.

2026-08-16 중간 QA에서 확인된 수정 대상은 다음 7개다.

- 셀 경계 오염: `warrior_t04_c01` 강철 양단, `warrior_t05_c01` 대검 절단, `warrior_t07_c01` 맹호 참격, `warrior_t12_c01` 거인 가르기
- 중심축 흔들림: `warrior_t06_c02` 거인철퇴, `warrior_t03_c03` 맹진 찌르기, `warrior_t13_c03` 철혈 관통

수정 배치:

- 빌더: `build_warrior_motion_slicing_revision.mjs`
- 프롬프트: `warrior-motion-slicing-revision-prompts.json`
- 작업 ID: `warrior-motion-slicing-revision-jobs.json`
- 출력: `custom-assets/warrior-motion-slicing-revision/`

경계 수정은 각 셀을 독립된 최종 화면으로 취급하고, 인접 행의 잔상·별도 하단 띠·어긋난 지면선을 네거티브 조건으로 막는다. 중심축 수정은 F04-F14의 구조적 소실점과 주 발광핵을 `x=50%`에 고정하고, 핵심 밝기 중심을 `x=48%-52%` 범위로 제한한다. 바깥 잔해는 비대칭일 수 있지만 관통축·수직 충돌 기둥·주 접촉점은 좌우로 이동하면 안 된다.

- 도적 직업 순차 감시: `14542`

- 마법사 직업 순차 감시: `26468`
- 성직자 직업 순차 감시: `52931`

- 도적 품질 수정본: `1706`
- 전 직업 프레임 감사: `79893`

순찰자 이후는 한 직업당 하나의 셸이 c01→c05 순서로 `sync_sprite_sheets.mjs`를 실행한다. 첫 계열이 끝나면 다음 계열 감시가 자동 시작된다. 지속 세션이 실제로 종료됐고 해당 작업 JSON에 `queued` 또는 `running`이 남아 있을 때만 같은 명령을 다시 실행한다.

`sync_sprite_sheets.mjs`는 다음 항목을 모두 검증한다.

- PNG 1444×640
- PNG bit depth 8, color type 6(RGBA)
- `mode=detailed`
- frameWidth 361, frameHeight 160
- frameCount 16, columns 4, rows 4
- fps 16, loop false

감시 중 품질 수정 `catalogId`가 작업 JSON에 추가될 수 있으므로, `sync_sprite_sheets.mjs`는 각 폴링 시점에 작업 매니페스트를 다시 읽는다. 이 동적 재로드는 게이트웨이나 실행 중인 `activeJobId`를 중지·재시작하지 않는다.

`watch_sprite_audits.mjs`는 도적부터 성기사까지 새로 동기화된 PNG를 찾아 `evidence/all-class-sprite-audits/<batch>/<catalogId>/`에 16프레임 몽타주와 수치 보고서를 자동 생성한다. 이 감시는 생성·동기화 작업을 변경하지 않으며, ready 승격은 여전히 사람이 몽타주와 웹 재생을 확인한 뒤 결정한다.

도적 c02 시각 검수에서 80~90% 구간의 회전꽃이 자동 우선순위에서 빠진 사례가 확인되어 `peakMirrorPriority`는 F08/F09 좌우 알파 대칭률 80% 초과로 강화했다. F12 이후 평균 알파와 점유가 함께 소폭 증가하는 경우도 `lateEnergyRegrowth`로 표시한다. 이 신호는 불합격 자동 판정이 아니라 사람 검수 대상을 넓히는 용도다.

`summarize_sprite_audits.mjs`는 누적된 모든 감사 보고서를 하나의 JSON으로 모아 신호별 개수와 F01/F08/F09/F12/F13/F16 핵심 수치를 요약한다. 이 요약도 자동 ready 판정으로 사용하지 않고 시각 검수 대상을 놓치지 않기 위한 색인으로만 쓴다.

`inspect_sprite_runtime.mjs`는 모든 기본·수정 작업 JSON의 각 job ID를 게이트웨이에 읽기 전용으로 조회해 실제 queued/running/completed/failed/cancelled/missing 수, active catalogId, 직업별 PNG 수를 전수 요약한다. `/api/health`의 최근 30개 표시만으로 전체 큐를 판단하지 않는다.

또한 전체 job ID 중복, 동시 running 수, `activeJobId` 추적 여부를 검증한다. running 작업의 `updatedAt`이 10분을 초과해야만 `stale-active-job`으로 보고하며, 그 전에는 생성이 몇 분간 같은 진행률에 머물러도 중단·재시작하지 않는다.

FrameSmith 게이트웨이는 FIFO이며 작업 우선순위 변경 API가 없다. `activeJobId`가 있으면 절대 중지·재시작·교체하지 않는다. 게이트웨이 자체를 재시작하면 구현상 기존 `queued`/`running` 작업이 실패로 정리되므로, 수백 개 큐가 남아 있는 동안 게이트웨이를 예방적으로 재시작하면 안 된다. 실제 재시작 장애가 발생하면 각 `*-sprite-jobs.json`의 상태와 오류를 먼저 확인하고, 원본 프롬프트 매니페스트에서 누락된 `catalogId`만 새 작업 ID로 복구한다.

전사 Android 승격은 다음 도구만 사용한다.

```bash
python3 tools/vfx-lab/sync_warrior_sprites_to_android.py
```

도구는 웹 ready Map을 원본으로 100개 `catalogId`를 재생성하고, 매 파일의 WebP 형식·1444×640 RGBA·알파 일치를 검증한 뒤 임시 파일을 원자적으로 교체한다. 2026-08-17 전사 100종 실측에서 Q85는 무손실 WebP 145,571,066 bytes에서 53,742,592 bytes로 63.08% 감소했고, 알파 오차는 0이었다.

이후 다른 직업의 Android 승격 도구를 만들 때도 동일한 Q85 상수·알파 일치 검증·임시 파일 교체 방식을 재사용한다. 화질 기준을 바꾸려면 함수 호출부가 아니라 동기화 도구의 고정 상수와 이 문서를 함께 변경한다.
